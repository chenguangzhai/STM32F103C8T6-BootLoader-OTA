# STM32 OTA 串口助手 2.0

专为这个 OTA BootLoader 工程写的串口调试工具，替代 SSCOM。

## 2.0 变更（相对 1.0）

| 项 | 1.0 | 2.0 |
|---|---|---|
| 串口 | 单路 | **双路 A / B**，可同时打开、同时接收 |
| 双串口开关 | — | 顶栏勾选「双串口（显示串口 B）」：取消后隐藏 B 区、断开 B 口、发送目标只剩 A，退化为单串口布局；再勾上恢复 |
| 接收区 | 一个 | 左右两个，各自端口 / 波特率 / 显示模式 / 时间戳 / 自动滚动 / 清空 |
| 日志颜色 | 一份 | 仍是一份，「设置」改一次两个接收区同时生效 |
| SWD 复位 | 一个 | **每区各一套**：各自「复位目标」下拉 + SWD 复位 / 唤醒，只复位本路那块板 |
| 固件发送 | 发当前串口 | 「发送到」下拉单选 A / B；勾了「发送前调试器复位」就复位该路调试器 |
| 文本发送 | 发当前串口 | 底部发送栏「发送到」下拉单选 A / B（不广播） |
| 配置键 | port / baud / … | port1/port2、baud1/baud2…；1.0 的旧键会自动当作 A 路读取 |
| Ctrl+L | 清空接收区 | 清空**两个**接收区（串口缓冲与解析状态都不动） |

「保存日志」改到各接收区右键菜单里（保存本区），两个区的日志互不混淆。

## 为什么不用 SSCOM

| 痛点 | SSCOM | 本工具 |
|---|---|---|
| 中文日志显示成 `寮曡剼` | 固定 GBK，无法切换 | 固定 UTF-8，可切 GBK / HEX |
| 发固件要手动分块、计时 | 无内建文件发送 | 选 bin 直接发，块大小 / 延时可调 |
| 进度全靠数日志行 | — | 解析 `[ota] page ... sum: N` 自动算进度 |
| 丢没丢数据不知道 | — | 文件大小 vs `sum` 自动对账 |
| 升级完要按板子复位键 | — | **SWD 复位**（经 DAP-Link），全自动 |
| 每次打开都拉一次 DTR | 会（可能误复位） | 打开时 DTR/RTS 保持低，不打扰板子 |
| 红色 FAIL 日志选不中、复制不了 | 部分版本禁用选择 | 接收区只读但可选中，右键还能一键复制全部日志 |

## 复位方式：必须走 SWD，串口 DTR 不行

调试器的 CDC 串口只透传 TX/RX，**DTR/RTS 根本没有接到 MCU 的 NRST**，
所以串口侧的 DTR 脉冲是空操作 —— SSCOM 里勾 DTR 也照样没反应。

真正有效的是通过 SWD 让调试器复位芯片。本工具调用 EIDE 自带的 OpenOCD：

```
openocd -f interface/cmsis-dap.cfg -f target/stm32f1x.cfg \
        -c "init; reset run; shutdown"
```

一次干净的单脉冲，实测复位后日志只出现一组 `[rst]`，不会像按键抖动那样打好几遍。

### 换调试器不用改配置

启动时会读当前插着的 USB 设备，自动换成对应的 interface 脚本：

| 调试器 | USB VID:PID | interface 脚本 |
|---|---|---|
| DAP-Link / DAPLink | 1FC9:5601、1FC9:0132、0D28:0204 | `cmsis-dap.cfg` |
| ST-Link V1 / V2 / V2-1 / V3 | 0483:3744 / 3748 / 374B / 374D / 374E / 374F | `stlink.cfg` |
| J-Link | 1366:0101、1366:0105 | `jlink.cfg` |

面板底部绿字会显示实际认到的设备名，比如 `SWD 复位就绪 · ST-Link V2`。

判断依据是 **CFGMGR32 的 PRESENT 过滤**，只认此刻真的连着的设备。
不能用注册表 `Enum\USB` 判断 —— 拔掉的设备键还留在里面，换调试器时
会认成旧的那个，然后复位必然失败（这是我自己踩过的）。

认错了、或者用的是表里没有的设备，在 `assist_config.json` 里手写一行覆盖：

```json
"ocd_iface": "stlink"
```

### 同时插两块板：选择「复位目标」

两台板子各带一个调试器同时插着时，OpenOCD 默认只认**第一个**匹配的调试器 ——
于是两个串口助手实例都会去复位同一块板，另一块毫无反应，看起来就像"识别不到"。

「固件发送」卡片里因此多了一个 **复位目标** 下拉框：

- 第 1 项 `自动（第一个）`：不指定序列号，行为和以前一样
- 之后每台在位调试器各一项，形如 `ST-Link V2-1 · 00078851`（序列号末 8 位，
  完整串显示在下方提示行里）
- 选中后立刻写进 `assist_config.json` 的 `ocd_serial`，并自动切到该设备对应的
  interface 脚本（DAP-Link → `cmsis-dap.cfg`、ST-Link → `stlink.cfg`）
- **点开下拉会自动重扫一遍 USB**：刚插上的板子不用先点「刷新软件」
  （那个会断串口、清日志，代价太大）

实现上就是给 OpenOCD 加一句 `adapter serial <序列号>`（放在 `-f interface/*.cfg`
之后、`init` 之前）。实测结果：

| 情况 | 现象 |
|---|---|
| DAP-Link 填对序列号 | `CMSIS-DAP: FW Version = 2.0.0`，连接成功 |
| ST-Link 填对序列号 | `STLINK V2J48M35 (API v2) VID:PID 0483:374B`，连接成功 |
| 填一个不存在的序列号 | DAP-Link 报 `unable to find a matching CMSIS-DAP device`；ST-Link 报 `open failed` |

最后一行正是它生效的证据——参数确实在按序列号过滤，而不是被忽略。

序列号取自 Windows 设备节点 ID 的最后一段：

```
USB\VID_0483&PID_374B\AE5A5BB50000000000078851   →  AE5A5BB5...（真序列号）
USB\VID_0483&PID_374B&MI_00\8&12225435&0&0000    →  跳过（接口节点，末段是拓扑编号）
```

复合设备的接口节点末段是"总线拓扑编号"，同型号设备之间会重名、重插还会变，
必须跳过 —— 否则同一台设备会被认成好几台，序列号还全错。

两个要留意的点：

1. **锁定的那块被拔掉**时，底部会红字提示"锁定的调试器不在位"，这时点复位会
   失败。这是有意的：宁可报错，也不静默换成另一块板去复位。
2. 两个串口助手实例共用同一份 `assist_config.json`，`ocd_serial` 也是共用的。
   运行期间各实例按自己内存里的选择走；重启后读到的是最后写进去的那个，
   重新选一下即可。

#### 换了调试器，不用重启软件 —— 点「刷新软件」

探测只在启动时做一次，中途把 DAP-Link 换成 ST-Link，按钮和提示不会自己变，
以前只能关窗重开。顶部栏的 **刷新软件** 就是软件内的"软重启"：

- 重新跑一遍调试器探测，同步 SWD 复位按钮的可用性、底部提示文字和颜色
- 断开已连的串口、清掉接收区日志和 OTA 解析状态、重扫串口列表
- 固件路径、窗口位置、各配置勾选**保留**（等价于真重启后从 json 恢复）

刷新后会打一行回执，比如 `调试器：ST-Link V2-1 → interface/stlink.cfg，SWD 复位就绪`。
注意：如果 `assist_config.json` 里手写了 `ocd_iface`，配置优先于探测结果，
刷新不会覆盖它（那是"认错了"的逃生口）—— 想换回自动识别就把这行删掉再刷新。

### ST-Link 的坑：报 open failed

OpenOCD 通过 libusb 访问 ST-Link，而 STM32CubeProgrammer / ST-Link Utility
装的官方驱动会独占设备，两者不能共存。表现就是复位失败，
OpenOCD 报 `Error: open failed`（我实测指定 stlink 时就是这个报错）。

三种解法，按省事排序：

1. 换 **ST-Link V2-1 或 V3**（Nucleo 板载那种）—— 走 HID，通常免驱直接用
2. 用 Zadig 把 ST-Link 的接口驱动从 ST 官方换成 **WinUSB**
3. 继续用 DAP-Link —— 兼容性最好，本工程全程用它验证

**找不到 OpenOCD、或认到的调试器在 OpenOCD 里没有对应脚本时**，
按钮自动置灰，面板底部用红字说明原因，此时手动按板子复位。

## 运行

**方式一：exe（免装 Python，推荐拷给别人用）**

双击 `dist\STM32_OTA_SerialAssist.exe`。

单文件打包，第一次启动要先把 tkinter 解包到临时目录，比源码版多等 1~2 秒，
之后每次启动都是这个速度（没有缓存加速）。体积约 10 MB，因为 Python 运行时
和 Tcl/Tk 都打进去了。

配置写在 **exe 同目录** 的 `assist_config.json`。换机器时把 exe 和这个 json
一起拷走，串口、波特率、块大小、窗口位置都能带过去。exe 改名不影响运行。

**方式二：源码运行（改代码时用）**

双击 **`run_serial_assist.bat`**。

需要 `C:\Python311`（自带 tkinter + pyserial）。若装在别处，改 bat 里的路径，
或直接：

```
python serial_assist.py
```

首次运行会在同目录生成 `assist_config.json`，记住串口、波特率、块大小、
窗口位置，下次打开自动恢复。

## 打包成 exe

改完代码后重新打包（约 15 秒）：

```
cd Tools\SerialAssist
C:\Python311\python.exe -m PyInstaller --noconfirm --onefile --noconsole ^
  --name STM32_OTA_SerialAssist --icon serial_assist.ico ^
  --hidden-import serial.tools.list_ports_windows ^
  --exclude-module PIL --exclude-module numpy ^
  --exclude-module matplotlib --exclude-module pandas ^
  --distpath dist --workpath build serial_assist.py
```

产物在 `dist\STM32_OTA_SerialAssist.exe`。

几个参数不是随便写的：

- `--noconsole`：GUI 程序，不带它每次启动会弹一个黑框
- `--hidden-import serial.tools.list_ports_windows`：pyserial 的 Windows
  端口枚举后端是运行时按平台动态导入的，静态分析扫不到。漏了它程序照样能启动，
  但端口列表永远是空的 —— 这是打包串口工具最典型的坑
- `--exclude-module PIL/numpy/...`：这些只是我生成图标时用过，运行时不需要，
  排掉能省几 MB

打包后务必自检一遍，确认端口枚举没被漏掉：

```
dist\STM32_OTA_SerialAssist.exe --check
```

正常输出类似：

```
UI self-check OK: 1280x900
serial ports(7): COM25, COM13, COM14, COM3, ...
config: ...\dist\assist_config.json
```

注意最后一行必须是 exe 所在目录，**不能**是 `C:\Users\...\AppData\Local\Temp\_MEIxxxx`。
如果指向了 Temp，说明 `app_dir()` 被改坏了，配置每次关窗都会丢。

## 复制日志（包括红色 FAIL 行）

接收区虽然不允许改写，但**可以正常选中和复制**：鼠标拖选后 `Ctrl+C`，
或右键 →「复制选中」/「复制全部日志」。失败行的红色只是文字颜色，
不影响复制。

> 实现上这里踩过坑：Tk 的 `Text` 一旦设为 `disabled`，用户连选中都做不到，
> 所以现在控件保持 `normal`，由按键白名单吞掉 BackSpace / Delete / Ctrl+V
> 等编辑键，保证「只读」和「可复制」同时成立。

第二个坑是**选区高亮被标签盖住**：`bad` 标签带浅红背景，Tk 里它的优先级
高于内置 `sel`，拖选时红字行仍是浅红底，看着像没选中（其实已在选区里）。
现在已显式把 `sel` 提到最高优先级，红字行选中时同样变蓝底，文字仍按来源着色。

## 自定义日志颜色规则

顶部栏 **设置** 按钮打开规则窗口。默认六条规则，全部可改；还能自己新增，
换工程时改规则就行，不用改代码、不用重打包。

**规则怎么匹配**：一条规则 = 关键词 + 字色/底色。关键词用 `|` 分隔多个，
一行日志含其中任意一段就命中。规则**自上而下匹配，首命中即停**——
所以顺序就是优先级，用 ↑↓ 调整。比如把 `[can]` 规则移到 FAIL 上面，
`[can] init FAIL` 就会按 CAN 的颜色显示，而不是红色。

窗口操作：选中一条 → **编辑** 改名称/关键词/字色/底色（也可双击）；
**新增** 加规则；**删除** 删选中规则——**包括默认六条，全部都能删**，
删错了点「恢复默认」一键找回；**↑ / ↓** 调顺序；下方预览区实时显示每条规则的示例行。
删光所有规则也不会出错，只是日志都不着色（显示默认字色）。

| 内置规则 | 关键词 | 默认字色 |
|---|---|---|
| FAIL / ERROR | `FAIL\|ERROR\|error` | `#D93025` 红（底色 `#FDECEA`） |
| `[boot]` | `[boot]` | `#7C3AED` 紫 |
| `[ota]` | `[ota]` | `#0E7490` 青 |
| `[rst]` | `[rst]` | `#C77700` 橙 |
| ok / OK | ` OK` | `#0F9D58` 绿 |
| 系统提示 | 留空（不参与匹配） | `#6C7683` 灰 |

`系统提示` 默认是工具自己打的行（`---` / `>>>` 开头）和 HEX 模式专用，
关键词留空；但它同样可以改关键词、改颜色，甚至删掉——删掉后那些提示行
失去灰色、显示默认字色（不会报错）。改完点 **确定** 立即生效——屏幕上
已有的日志也会按新规则重新着色；**取消** 则一点不动。有「恢复默认」一键回到上表。

**换工程怎么带走**：整套规则存在 exe 同目录 `assist_config.json` 的 `log_rules`
列表里，把这个 json 拷到新工程、和 exe 放一起就全带过去了。非法色值（不是
`#RRGGBB`）、非法 tag 名、占用 Tk 内置 `sel` 的规则都会被安全忽略或回退默认，
不会让软件起不来。老版本只有 `log_colors` 字典的配置也能自动升级，改过的颜色不丢。

## 清空接收（Ctrl+L）

状态栏右下角「清空接收」只清接收区这一屏字，**串口一个字节都不动**。

| 保留的东西 | 为什么不能清 |
|---|---|
| 驱动层 `in_waiting` | 板子刚发来、驱动已收到但还没读的字节 |
| `rx_queue` | 已读到、还没渲染的块 |
| `line_buf` | 跨块的半行，解析器靠它把一行拼完整 |
| 增量解码器 | 可能正存着半个多字节字符 |
| `rx_count` / `tx_count` | 累计收发统计 |

所以清完之后只要板子还在发，屏幕会接着往下滚 —— **清屏不等于停收，
更不等于丢板子的数据**。实测：清屏瞬间队列里压着 6 块，4 秒后 380 B
全部补上屏，一行没少。

唯一动到的"数据"是 HEX 模式下的偏移：清屏后从 `00000000` 重新起算。
不归零的话第一行会接着上一屏的地址，看起来像中间丢了一段，反而更迷惑。

## 固件路径记忆与检查更新

**选择 .bin 文件** 打开的目录会自动定位到上次选过的固件所在目录；
路径在选完的瞬间就写进 `assist_config.json`，不等关窗——程序崩了也不丢。
上次那个文件如果已被删掉，会退到它的父目录；再不行才回退到工程的
`Application/build/Debug`。

旁边的 **检查更新** 按钮用于"重新编译后不用重新选文件"：它对比当前选中
bin 的**修改时间和大小**，任一变化就自动重新装填——刷新大小显示、重置解析
状态，并在接收区打两行提示（装填 + 旧大小→新大小）。没变化也会打一行说明，
不弹窗打断。文件被删则按钮置灰并提示。**没选文件时按钮禁用**。

只比 mtime/size 不读内容算 CRC：发送时本来就会读一遍，检查按钮没必要重复。
注意"内容变了但大小和时间戳都没变"这种极特殊情况检测不到——正常重新
编译一定会更新 mtime，所以实际够用。

## 一次完整 OTA 升级（全自动，不用碰板子）

1. 点 **刷新**，选中端口（真实 USB 口会排在最前，蓝牙虚拟口排在最后），
   波特率 115200，点 **打开串口**
2. 点 **选择 .bin 文件**，选 `Application/build/Debug/Application.bin`
   （默认会直接打开上次那个目录）
   重新编译后不用重选，点旁边的 **检查更新** 即可自动装填最新固件
3. 块大小 **256**、块延时 **1ms**——这是实测能稳定收的组合
4. 保持 **发送前调试器复位** 勾选
5. 点 **开始发送**

接下来全自动：

```
SWD 复位            → [ota] ready, proto=2，进入 3 秒窗口
发 14,868 B         → [ota] page ... 逐页落盘
发 12 字节尾部      → [ota] tail: len=14868 crc=0x7D7DF238
MCU 读回 Flash 校验  → [ota] verify OK 14868B，参数页写入 {长度, CRC}
MCU 自己跳转        → [boot] jump to app
```

实测全程 **1.46 秒**（原来要 9.1 秒），最后那次复位彻底省掉了。

接收区日志会依次出现 `[ota] ready` → `[ota] page ... ok` →
`[ota] tail:` → `[ota] verify OK`，全程不用按键。

⚠️ 如果日志出现 `[ota] verify FAIL`，说明 Flash 里的内容和发出去的对不上。
板子会停在 OTA 等重传，直接再点一次发送即可，**不用复位**。

### 尾部记录：12 个字节

固件发完之后补 12 字节，告诉 MCU「发完了、共多少、CRC 多少」：

| 偏移 | 内容 |
|---|---|
| 0..3 | `OTAE` |
| 4..7 | 固件长度，小端 |
| 8..11 | CRC32，小端 |

MCU 判定时不只看 magic，还要求**声明的长度必须等于已收字节数**，
两个条件同时满足才认。固件里恰好出现 `OTAE` 的概率约 2⁻³²，
再叠上长度约束，实际误判可以忽略。

CRC 是 MCU **把 Flash 读回来重算**的，不是边收边算。这点很关键：
边收边算只能证明「我收到了什么」，证明不了「Flash 里存的是什么」。
擦除不干净、写入被打断、电压跌落，都会让两者不一样。

### 为什么现在不用再复位了

`proto=1`（加校验之前的 BootLoader）收完固件后不会自己跳，工具得补一次复位。
`proto=2` 之后 MCU 自己完成「校验 → 写参数 → 跳转」，工具只管发数据。

工具靠 `[ota] ready` 末尾有没有 `proto=2` 来区分：
新工具配老 BootLoader 会**自动退回**老流程（等 sum 对齐再复位），
不会因为多发 12 字节把固件写坏。

### 上电时的判断顺序

复位后 BootLoader 按这个顺序决定跳不跳：

```
1. 向量表像不像样         SP 在 RAM？复位向量在 Flash？   不像 → 停在 OTA
2. 参数页有没有内容       全 0xFF = 从没写过              空 → legacy 模式，跳但不保证
3. 参数页自身有没有写坏    magic + self_crc               坏 → 停在 OTA
4. 固件到底对不对         读回 Flash 重算 CRC 比对        不对 → 停在 OTA
```

第 2 步的 legacy 模式是给「加校验之前刷进去的老固件」留的退路 ——
否则刷完新 BootLoader 会发现自己的 App 起不来了，像被刷砖了一样。
日志里会写 `[boot] no param, unverified app`，提示这份固件没被验证过。

### 为什么不能"发完就立刻复位"

最后不足一页的 tail（本例 532 B）要等 BootLoader 的**空闲超时**才落盘，
这个时间不受上位机控制。发完立刻复位会把 tail 截断，Flash 里只留下半截固件
（表现为 `sum` 停在最后一页边界，例如 14336）。
所以工具是盯 `sum` 而不是靠固定延时。

## 日志怎么读

工具会解析这几类行，用于内部进度判断（OTA 状态面板已移除，日志原文照常显示在接收区）：

| 日志 | 含义 | 内部作用 |
|---|---|---|
| `[ota] ready, app=0x08008000, page=2048B, proto=2` | BootLoader 就绪 | 读协议版本；**升级刚完成时的那次不会清零已落盘计数** |
| `[ota] page 0x... ok, sum: N` | 一页落盘 | 更新已落盘字节数 |
| `[ota] tail 0x... xxxB ok, sum: N` | 尾块落盘 | 更新已落盘字节数，标记升级完成 |
| `[ota] verify OK / FAIL` | CRC 校验结论 | 决定后续是否继续等待/复位 |
| `[boot] ...` / `[rst] ...` / `[can] ...` | 其它状态日志 | 只着色显示，可选中复制，不参与发送决策 |

SWD 复位会同时报 `PIN` 和 `SFT`：OpenOCD 发的是 SYSRESETREQ（软件复位请求），
芯片内部会顺带把 NRST 拉一次，所以两条都置位。这是正常的，
只有单独一条 `PIN` 且反复出现好几次，才是按键抖动。

## 常见问题

**打开串口报"被占用"**
SSCOM / XCOM / VSCode 串口监视器还开着。关掉它们。

**SWD 复位没反应**
0. 刚换过调试器？先点 **刷新软件** —— 不刷新的话软件还按旧 interface 脚本走
0.1 电脑上插了两块板？看 **复位目标** 下拉选的是不是你要复位的那块 ——
   选 `自动（第一个）` 时 OpenOCD 只会认第一个调试器，两块板会一起"复位同一块"，
   另一块自然毫无反应。底部红字"锁定的调试器不在位"也属于这一类。
1. 板子没上电 / USB 只接了串口没接 SWD
2. DAP-Link 被别的程序占着 —— VSCode 的 Cortex-Debug、Keil、STM32CubeProgrammer
   同时只能用一家，先断开调试会话
3. 面板底部如果是红字"未找到 OpenOCD"，说明 EIDE 工具链路径变了，
   重装 EIDE 的 OpenOCD 或改脚本里的 `find_openocd()` 候选路径

**发完不自动跳 App**
先看接收区日志：老协议要等 `[ota] page/tail ... sum` 追上文件大小，
新协议要看到 `[ota] verify OK`。若 sum 一直停在某个值，
说明 tail 没落盘就去复位了 —— 本工具已经改成等 `sum` 确认，正常不会发生。

**中文还是乱码**
本工具固定按 UTF-8 解，正常不会乱。若源码里有 GBK 字符串，
把右上角"显示"切成 GBK 看。
